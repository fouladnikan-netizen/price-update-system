# گزارش بررسی برندها و رابطه با کاتالوگ

**وضعیت:** بررسی فقط‌خواندنی — هیچ فایل Excel، کاتالوگ، دیتابیس، Seed یا ساختار پروژه تغییر نکرده است.  
**منبع برند:** `data/brands/`  
**منبع کالا:** `data/products/catalog.xlsx` (بدون تغییر)  
**تاریخ بررسی:** ۱۹ اوت ۲۰۲۶  
**`product_code` جدید:** ساخته نشده است.

**نتیجه کلی:** برندها محصول مستقل نیستند و باید به‌صورت تگ وابسته به محصول پایه ثبت شوند. کلید اتصال قیمت به Website در این مدل `product_code + brand_id` است، **به شرطی که** `product_code` همان کد محصول پایه Website بماند و `brand_id` از تگ برند Website بیاید. فایل برند فعلی برای Seed کامل آماده نیست: شناسه برند ندارد، نام‌ها یکدست نیستند، و برای حدود دو سوم دسته‌های کاتالوگ جدول برند وجود ندارد.

---

## مدل ارتباطی مبنای این بررسی

طبق توضیح جدید Website:

```text
محصول پایه (product_code)     مثال: نبشی ۴
        │
        ├── تگ برند (brand_id)   مثال: شکفته
        └── تگ برند (brand_id)   مثال: بناب

نمایش:  نبشی ۴ شکفته
        نبشی ۴ بناب

مشاهده قیمت (price observation) وابسته است به:
        product_code + brand + نوع قیمت + تاریخ
```

نتیجه معماری:

| موجودیت | هویت | نقش |
| --- | --- | --- |
| محصول پایه | `product_code` Website | سایز/نوع کالا؛ برند داخل آن نیست |
| تگ برند | `brand_id` | کارخانه/تولیدکننده مجاز برای آن کالا یا دسته |
| مشاهده قیمت | کلید ترکیبی | قیمت کارخانه یا انبار برای همان کالا × همان برند |
| انتشار Website | همان کلید ترکیبی | کد محصول پایه عوض نمی‌شود |

نمونه قبلی بریف (`REB-A3-14-ESF`) که برند را داخل `product_code` می‌گذاشت، با این مدل Website **هم‌خوان نیست** و نباید مبنای Seed باشد.

## ۱) فایل‌های داخل `data/brands/`

| مسیر | نوع | حجم | تاریخ فایل |
| --- | --- | ---: | --- |
| `data/brands/Brand.numbers` | Apple Numbers (بسته ZIP) | ۲۶۳٬۰۵۴ بایت | ۱۲ اوت ۲۰۲۶ |

فایل دیگری در این پوشه نیست. Excel، CSV یا یک فایل جدا برای هر گروه وجود ندارد.

انتظار بریف/توضیح اخیر این بود که «برای هر گروه محصول یک فایل یا جدول برند باشد». وضعیت واقعی:

- **یک فایل** برای همه گروه‌ها
- داخل همان فایل **۱۷ جدول** هست
- جدول‌ها بیشتر در سطح **دسته** هستند، نه هفت گروه اصلی

این فایل به‌خاطر فرمت Numbers برای Seed مستقیم مناسب نیست؛ فعلاً فقط خوانده شده و تبدیل یا کپی نشده است.

جدول `ورق آلیاژی` در فایل برند هست، اما چنین دسته‌ای در کاتالوگ نیست. احتمالاً باید روی چند دسته آلیاژی کاتالوگ نگاشت شود؛ این نگاشت تأیید نشده است.

### مقایسه با شیت وزن تیرآهن کاتالوگ

شیت `تیرآهن-وزن-برند` در کاتالوگ ۱۰ برند وزن دارد. این‌ها تگ محصول نیستند؛ جدول وزن‌اند. با جدول برند تیرآهن:

| برند وزن کاتالوگ | اسلاگ | معادل در جدول برند تیرآهن |

| فایکو | `faico` | تیرآهن فایکو |
| یزد | `yazd` | تیرآهن یزد |
| کرمانشاه | `kermanshah` | تیرآهن کرمانشاه |
| ظفر بناب | `zafar-bonab` | تیرآهن ظفر بناب |
| آریان فولاد | `arian-foolad` | تیرآهن آریان فولاد |

### نشانه‌های برند داخل خود کاتالوگ کالا

کاتالوگ ستون برند ندارد، ولی چند مقدار `نوع` شبیه کارخانه است و نباید با تگ برند قاطی شود مگر تأیید شود:

- `ورق فولاد مبارکه` / `ورق گیلان` در پروفیل زد
- `از ورق فولاد مبارکه` / `از ورق گیلان` در لوله داربستی

Data Validation قدیمی کاتالوگ هم چند نام کارخانه دارد (شکفته، ناب تبریز، فایکو، پاسارگارد، هاردوکس، چین، …). این لیست‌ها با داده فعلی ستون `نوع` هم‌خوان نیستند و منبع برند شمرده نمی‌شوند.

## ۵) نام تکراری، متفاوت‌نویسی و ابهام

آمار یکتایی پس از نرمال‌سازی فاصله و نیم‌فاصله:

| شاخص | تعداد |
| ---: | --- |
| ردیف تگ | ۱۲۲ |
| نام بازاری خام یکتا | ۹۳ |
| نام کوتاه‌شده یکتا (بدون پیشوند کالا) | ۸۱ |
| نام حقوقی یکتا | ۸۱ |

تکرار نام بین جدول‌ها برای کارخانه واحد (مثل فولاد مبارکه روی ۹ دسته ورق) در مدل تگ **اشکال نیست**؛ همان `brand_id` باید به چند دسته وصل شود. مشکل وقتی است که یک نام به دو کارخانه اشاره کند، یا دو تگ داخل یک دسته یک کارخانه باشند.

### تکراری خطرناک داخل همان جدول

در جدول میلگرد، دو جفت تگ به یک نام حقوقی می‌رسند:

| تگ اول | تگ دوم | نام حقوقی مشترک |
| --- | --- | --- |
| میلگرد صنعت بناب | میلگرد فولاد شاهین بناب | مجتمع فولاد صنعت بناب |
| میلگرد گروه ملی | میلگرد فولاد کوثر اهواز | گروه ملی صنعتی فولاد ایران |

اگر Website برای هر کارخانه یک تگ دارد، یکی از این جفت‌ها نام بازاری است نه هویت جدا. اگر Website هر دو را جدا می‌داند، نام حقوقی فایل برند اشتباه یا ناقص است. تا تأیید Website نباید ادغام یا حذف شوند.

### یک نام کوتاه، دو کارخانه مختلف

| نام کوتاه | جا | کارخانه |
| --- | --- | --- |
| یزد | تیرآهن / میلگرد احرامیان | نورد فولاد صنعتی و ساختمانی یزد |
| یزد | نبشی یزد | فولاد دهشیر یزد |
| بافق یزد | میلگرد | فولاد بافق یزد (سوم) |
| کاشان | ورق گالوانیزه / عرشه / شیروانی | فولاد امیرکبیر کاشان |
| کویر کاشان | میلگرد و میلگرد ساده | سپید فراب کویر |
| اهواز | لوله مانیسمان | گروه ملی، کارخانه لوله |
| کوثر اهواز / گروه ملی | میلگرد و تیرآهن | گروه ملی صنعتی فولاد ایران |
| اکسین اهواز | ورق | فولاد اکسین خوزستان |
| کاوه | لوله مانیسمان | لوله‌های دقیق کاوه ایرانیان |
| کاوه اروند / کاوه تیکمه‌داش | میلگرد | دو کارخانه دیگر |

پس `brand_id` را نمی‌شود از روی نام کوتاه تنها ساخت. «یزد» در تیرآهن و «یزد» در نبشی دو تگ جدا هستند.

### متفاوت‌نویسی و غلط املایی

| مورد | توضیح |
| --- | --- |
| پیشوند کالا داخل نام تگ | «میلگرد فایکو»، «تیرآهن فایکو»، «فایکو» هر سه یک کارخانه‌اند |
| ناب / ناب تبریز | تیرآهن: ناب ؛ نبشی و ناودانی: ناب تبریز |
| آریان / آریان فولاد | میلگرد: آریان ؛ بقیه: آریان فولاد |
| ظفر بناب | میلگرد: مجتمع فولاد ظفر بناب ؛ تیرآهن: شرکت فولاد ظفر بناب |
| قائم / قایم | نام بازاری «قائم رازی» و نام حقوقی «قایم پروفیل رازی» |
| پاسارگاد / پاسارگارد | فایل برند: پاسارگاد ؛ Validation قدیمی کاتالوگ: پاسارگارد |
| جهان  سیرجان | دو فاصله پشت‌سرهم |
| فولاد غرب اسیا | «آسیا» بدون «آ» |
| نبشی زنجان | «نشرکت ورد یاوران زنجان»؛ ظاهر غلط املایی «شرکت نورد …» |
| ذوب‌آهن اصفهان | جدول وزن کاتالوگ همین کارخانه را «اصفهان» نامیده |
| خیام / خیام نیشابور | جدول برند: خیام ؛ جدول وزن: خیام نیشابور |
| صنعت بناب / شاهین بناب | دو تگ بازاری، یک نام حقوقی |
| خلیج فارس / آتیه خلیج فارس | میلگرد ساده: میلگرد خلیج فارس ؛ میلگرد: آتیه خلیج فارس ؛ هر دو به فولاد آتیه خاورمیانه نزدیک‌اند |

### نام‌های مبهم به‌عنوان برند

- `چین` برای لوله مانیسمان یعنی کالای وارداتی، نه کارخانه.
- `هاردوکس` و `NM` در ورق ضدسایش بیشتر گرید/استانداردند تا کارخانه. در کاتالوگ همین دسته، ستون `نوع` مقدار «سختی ۴۵۰ / ۵۰۰» دارد نه این تگ‌ها.
- `اسپیرال` در نبشی/ناودانی برند است؛ در کاتالوگ «لوله اسپیرال» دسته است. هم‌نامی خطر تطبیق غلط دارد.
- `کاشان` خیلی کوتاه است و با کویر کاشان قاطی می‌شود.

## ۶) مدل پیشنهادی داده (بدون اجرا)

```text
Product          1 ─── N  ProductBrandTag  N ─── 1  Brand
product_code                 allowed link              brand_id
standard_name                (دسته/کالای مجاز)         display_name
(بدون برند)                                            legal_name
                                                       aliases

PriceObservation
  product_code     → محصول پایه Website
  brand_id         → تگ برند Website
  price_type       → factory | warehouse
  price_date
  amount
  source_id
```

نمایش UI: `standard_name + display_name`  
مثال: پایه `نبشی ۴` + تگ `شکفته` → `نبشی ۴ شکفته`

قواعد:

- محصول پایه از کاتالوگ/Website می‌آید؛ برند آن را تکثیر نمی‌کند.
- یک برند می‌تواند روی چند دسته مجاز باشد (فولاد مبارکه روی چند ورق).
- هر مشاهده قیمت بدون `brand_id` ناقص است، مگر منبع صریحاً برند نداشته باشد؛ در آن صورت وضعیت باید «بدون برند / نیاز به بررسی» باشد، نه حدس نام.
- وزن برند×سایز (شیت تیرآهن کاتالوگ) موجودیت جدا است، نه جایگزین تگ برند.

## ۷) آیا `product_code + brand_id` برای اتصال به Website کافی است؟

**برای تمایز قیمت کالا × برند، بله؛ به‌تنهایی برای Seed امروز، خیر.**

کافی است اگر همه این‌ها برقرار باشد:

1. Website برای محصول پایه فقط یک `product_code` دارد (مثلاً نبشی ۴) و آن کد عوض نمی‌شود.
2. Website برند را تگ جدا با شناسه پایدار (`brand_id` یا معادل تگ) دارد.
3. API انتشار هم `product_code` و هم شناسه/نام تگ برند را می‌پذیرد.
4. سامانه قیمت `product_code` جدید نمی‌سازد و برند را داخل کد محصول قاطی نمی‌کند.
5. تگ‌های هم‌نام ولی کارخانهٔ متفاوت، `brand_id` جدا دارند.
6. مجموعه تگ مجاز هر کالا یا دسته مشخص است؛ هر برندی روی هر کالایی نمی‌نشیند.

کافی نیست اگر:

- کاتالوگ هنوز `product_code` Website ندارد (وضعیت فعلی).
- فایل برند `brand_id` ندارد و فقط نام فارسی دارد.
- API Website فقط `product_code` می‌گیرد و تگ برند را نمی‌پذیرد؛ در آن صورت نبشی ۴ شکفته از نبشی ۴ بناب قابل انتشار نیست.
- کسی بخواهد برای هر ترکیب کالا×برند یک `product_code` جدید بسازد؛ این خلاف مدل Website و خلاف دستور این مرحله است.

پیشنهاد قراردادی (اجرا نشده):

```text
انتشار روزانه:
  product_code     = کد محصول پایه Website
  brand_id         = شناسه تگ برند Website
  price_type       = factory | warehouse
  price
  unit
  price_date
  source_id
  approval_id
```

کلید یکتایی مشاهده و idempotency انتشار:  
`product_code + brand_id + price_type + price_date`  
نه `product_code` به‌تنهایی.

## ۱۰) تصمیم‌هایی که باید تأیید شوند

1. آیا شناسه تگ برند را باید از Website گرفت، یا تا زمان دریافت API فقط نام فارسی فایل Numbers معیار است؟
2. آیا تگ نمایشی باید بدون پیشوند کالا باشد؟ مثلاً `فایکو` به‌جای `میلگرد فایکو` / `تیرآهن فایکو`.
3. در میلگرد، «صنعت بناب» و «شاهین بناب» دو تگ Website هستند یا یک کارخانه با دو نام بازاری؟
4. «گروه ملی» و «کوثر اهواز» یک تگ‌اند یا دو تا؟
5. «یزد» تیرآهن و «یزد» نبشی باید دو `brand_id` جدا باشند؟
6. جدول `ورق آلیاژی` روی کدام دسته‌های کاتالوگ می‌نشیند (ST52، A36، A516، A283، آتشخوار)؟
7. تیرآهن هاش و ناودانی سنگین همان تگ‌های تیرآهن و ناودانی را دارند؟
8. برند پروفیل و بقیه لوله‌ها از کجا می‌آید؟ فعلاً در `data/brands/` نیست.
9. `چین`، `هاردوکس` و `NM` تگ برند مجازند یا باید نوع/گرید جدا باشند؟
10. برای پایلوت میلگرد، آیا فقط کالاهای پایه میلگرد آجدار + تگ‌های جدول میلگرد وارد می‌شوند و بقیه گروه‌ها می‌مانند؟

پس از تأیید این موارد می‌توان مرحله بعد را مشخص کرد. تا آن زمان Seed، Migration و تولید کد محصول انجام نمی‌شود.
