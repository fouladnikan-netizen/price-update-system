# قرارداد انتقال کاتالوگ Website به سامانه قیمت

**وضعیت:** سند قرارداد — اجرا نشده است.  
**اسناد قفل‌شده مبنا:**
- `docs/product-identity-contract.md`
- `docs/identity-key-decision.md`

**تاریخ:** ۱۹ اوت ۲۰۲۶

این قرارداد فقط قوانین Import کاتالوگ هویت را مشخص می‌کند. در این مرحله CSV، Excel، Website، دیتابیس، Migration، Seed و کد اجرایی تغییر نمی‌کنند.

---

## هدف Import

انتقال **هویت** محصول پایه، گروه، دسته، نام و تگ‌های برند از خروجی رسمی Website به سامانه قیمت.

Import کاتالوگ:

- قیمت روز، مشاهده منبع، بررسی انسان و انتشار نیست
- از متن آگهی/تلگرام/اکسل رقبا محصول یا برند نمی‌سازد
- `product_code` جدید تولید نمی‌کند

```text
خروجی رسمی Website
        │
        ▼
  اعتبارسنجی و گزارش
        │
        ├── رد: ناقص / تکراری / مبهم
        └── پذیرش
                │
                ▼
  product_groups → product_categories → products
                │
                ▼
  brands → product_brand_tags
```

## ۱) منبع داده

منبع اصلی هویت، **خروجی رسمی Website** است نه کاتالوگ Excel محلی سامانه قیمت.

ترتیب اولویت منبع:

1. CSV یا JSON صادرشده از Website که ستون کد کالا همان `sku` باشد.
2. در صورت دسترسی کنترل‌شده، خواندن مستقیم مجموعه `products` Website فقط به‌صورت خواندنی.

نمونه‌های شناخته‌شده خروجی Website (بدون الزام به استفاده از فایل خاص در این مرحله):

| خروجی | ستون کد | محدودیت |
| --- | --- | --- |
| `GET /api/admin/products/csv` | «شماره یکتا» = `sku` | برند کامل همه تگ‌ها را ندارد |
| `scripts/export-product-brand-list.mjs` → CSV | «کد یکتا محصول» = `sku` | گروه/دسته/برندها را دارد |
| CSV تگ برند یک کالا | `sku` + `brandSlug` | فقط برندهای همان کالا |

منبع **نیست**:

- `data/products/catalog.xlsx` سامانه قیمت
- `data/brands/Brand.numbers`
- `Final Product.xlsx` داخل Website
- متن قیمت کانال‌ها و سایت رقبا

اگر خروجی رسمی `sku` نداشته باشد، Import متوقف می‌شود. از نام کالا کد ساخته نمی‌شود.

فایل ورودی خام قبل از پردازش باید به‌عنوان ورودی حفظ شود (مسیر/کلید ذخیره + checksum + زمان دریافت). پردازش فقط روی رونوشت اعتبارسنجی‌شده انجام می‌شود.

## ۲) نگاشت هویت کالا

```text
Website.sku  →  PriceSystem.product_code
```

قواعد کپی:

1. فقط trim ابتدا و انتها.
2. هیچ بازنویسی، ترجمه، تغییر بزرگی/کوچکی معنایی، حذف پیشوند یا ساخت الگوی جدید مجاز نیست.
3. یک `sku` غیرتهی = یک محصول پایه.
4. `_id` مونگو `product_code` نمی‌شود، مگر در گزارش رد برای ردیفی که `sku` خالی است.
5. تگ برند مقدار کد را عوض نمی‌کند.

`source_of_code` برای همه ردیف‌های پذیرفته‌شده فقط `website` است.

---

## ۳) ممنوعیت ساخت کد جدید

Import حق ندارد:

- برای ردیف بدون `sku` کد بسازد
- از نام، گرید، سایز یا برند کد بسازد
- برای هر برند یک `product_code` جدا بسازد
- کد تکراری را با پسوند محلی یکتا کند
- کدهای پیشوند `RECOVERY-CLONE-` یا `STAGING-PILOT-` را به‌عنوان کاتالوگ رسمی بپذیرد

چنین ردیف‌هایی فقط در گزارش رد می‌آیند.

## ۴) انتقال محصول پایه، گروه، دسته و نام

### محصول پایه → `products`

| منبع Website | مقصد سامانه قیمت | قاعده |
| --- | --- | --- |
| `sku` | `product_code` | الزامی؛ کپی مستقیم |
| `name` | `standard_name` | الزامی؛ نام پایه بدون برند |
| دسته اصلی | `category_id` | از درخت دسته Website |
| `isActive` / `saleStatus` | `is_active` | `inactive` → غیرفعال |

مشخصات فنی (گرید، سایز، ضخامت، طول، وزن، واحد) اختیاری‌اند و هویت نیستند. اگر در خروجی باشند ذخیره می‌شوند؛ نبودشان مانع پذیرش هویت نیست، به شرط وجود `sku` و نام و دسته.

### دسته → `product_categories`

دسته از `ProductCategory` Website می‌آید (`titleFa`، `slug`، `parentId`).

- `code` دسته در سامانه قیمت از `slug` Website کپی می‌شود، ساخته نمی‌شود از روی نام فارسی.
- اگر `slug` نباشد، دسته وارد نمی‌شود و کالاهای وابسته رد می‌شوند.

### گروه → `product_groups`

Website جدول گروه جدا ندارد. گروه از نیای دسته (یا نگاشت پایدار `slug` نیاکان به هفت گروه اصلی) به‌دست می‌آید.

هفت گروه مجاز: میلگرد، تیرآهن، ورق، نبشی، ناودانی، پروفیل، لوله.

اگر نیای دسته به هیچ گروه مجاز نگاشت نشود، رکورد **مبهم** است و وارد نمی‌شود تا نگاشت تأیید شود. حدس آزاد از روی متن نام ممنوع است.

`brand_mode` دسته پس از اتصال تگ‌ها تعیین می‌شود:

- دسته‌ای که حداقل یک تگ برند فعال دارد → `branded`
- دسته‌ای که هیچ تگ برندی ندارد → `unbranded` (خطا نیست)

## ۵) تبدیل `brandIds` / `brandOffers` به `product_brand_tags`

برند محصول جدید نیست.

| منبع Website | مقصد |
| --- | --- |
| سند `Brand` | `brands` |
| `brandIds` و ردیف‌های فعال `brandOffers` | `product_brand_tags` با `scope = product` |

ترتیب تبدیل برای هر محصول پذیرفته‌شده:

1. مجموعه تگ = اتحاد `brandIds` و `brandOffers` که `isActive != false`.
2. `brandId` تکی فقط اگر در آن مجموعه نباشد، به‌عنوان تگ سازگاری اضافه می‌شود.
3. برای هر تگ، برند در محدوده **گروه و دسته همان محصول** پیدا یا ایجاد ارتباطی می‌شود.
4. یک ردیف `product_brand_tags` با `(product_id, brand_id)` نوشته می‌شود.
5. قیمت داخل `brandOffers.priceToman` در این Import ذخیره **نمی‌شود**. کاتالوگ هویت است نه قیمت روز.

`ProductTag` عمومی (`tagIds`) تگ کارخانه نیست و در این قرارداد به `brands` تبدیل نمی‌شود.

`warehouseOffer` محصول جدا و برند جدا نمی‌سازد. فقط بعداً می‌تواند روی همان `product_code` نوع قیمت `warehouse` را فعال کند؛ آن کار این Import نیست.

شناسه پایدار برند Website برای ذخیره در `website_brand_id`:

1. `Brand.slug` اگر غیرتهی باشد
2. وگرنه `Brand._id` به‌صورت رشته

سامانه قیمت `website_brand_id` را تولید نمی‌کند.

## ۶) تفکیک برند هم‌نام با گروه و دسته

کلید یکتایی برند داخل سامانه قیمت:

```text
(group, category, display_name)
```

`display_name` از `Brand.titleFa` پس از trim می‌آید.

نمونه‌ها:

| گروه | دسته | نام نمایشی | ردیف برند |
| --- | --- | --- | --- |
| تیرآهن | تیرآهن | یزد | جدا |
| نبشی | نبشی | یزد | جدا |
| ورق | ورق گالوانیزه | کاشان | جدا از کویر کاشان میلگرد |

ادغام دو تگ هم‌نام فقط اگر `website_brand_id` (slug یا id) یکی باشد **و** دامنه گروه/دسته صریحاً مشترک اعلام شده باشد. شباهت `officialNameFa` برای ادغام کافی نیست.

اگر یک `slug` برند در دو گروه با نام نمایشی یکسان بیاید ولی Website همان سند باشد، گزارش «نیاز به تأیید اشتراک تگ» ثبت می‌شود؛ ادغام خودکار بین گروهها انجام نمی‌شود.

---

## ۷) محصولات بدون برند

نبود برند خطا نیست.

اگر پس از مرحله تگ، مجموعه برند خالی باشد:

- محصول با همان `product_code` وارد می‌شود
- هیچ ردیف `product_brand_tags` ساخته نمی‌شود
- محل قیمت بعدی فقط `product_code` است
- دسته می‌تواند `unbranded` بماند

ساخت برند پیش‌فرض مثل «عمومی» یا «نامشخص» ممنوع است.

## ۸) فیلدهای اجباری و اختیاری

### برای پذیرش محصول

| فیلد منطقی | اجباری |
| --- | --- |
| `sku` / `product_code` | بله |
| `name` / `standard_name` | بله |
| دسته قابل نگاشت به گروه مجاز | بله |
| حداقل یک تگ برند | خیر |
| مشخصات فنی | خیر |
| وزن تقریبی | خیر |
| قیمت Website | خیر — وارد کاتالوگ هویت نمی‌شود |
| تصویر و SEO | خیر — خارج از دامنه Import هویت |

### برای پذیرش برند و تگ

| فیلد منطقی | اجباری برای ساخت تگ |
| --- | --- |
| نام نمایشی برند | بله |
| `slug` یا `_id` Website | بله برای `website_brand_id` |
| گروه و دسته محصول میزبان | بله |
| نام حقوقی | خیر |
| نام جایگزین | خیر |

ردیف تگ بدون نام برند یا بدون هویت Website در گزارش مبهم می‌آید و تگ ساخته نمی‌شود؛ خود محصول اگر بقیه فیلدها را داشته باشد می‌تواند به‌عنوان بدون‌برند بماند **فقط وقتی هیچ تگ معتبری نداشته باشد**. اگر بعضی تگ‌ها معتبر و بعضی مبهم باشند، محصول وارد می‌شود، تگ‌های معتبر وصل می‌شوند، تگ‌های مبهم رد می‌شوند.

## ۹) رکورد ناقص، تکراری، مبهم

هر ردیف ورودی دقیقاً یکی از وضعیت‌ها را می‌گیرد: `accepted`، `updated`، `unchanged`، `rejected_incomplete`، `rejected_duplicate`، `rejected_ambiguous`، `skipped_non_catalog`.

| وضعیت | نمونه |
| --- | --- |
| ناقص | `sku` خالی؛ نام خالی؛ دسته خالی |
| تکراری ورودی | دو ردیف فایل با یک `sku` و داده متناقض |
| تکراری ورودی سازگار | دو ردیف با یک `sku` و داده یکسان → یک بار پذیرفته؛ تکرار در گزارش |
| مبهم | گروه نامشخص؛ برند هم‌نام بدون هویت Website؛ `sku` یکسان با نام/دسته متفاوت نسبت به رکورد قبلی سیستم در حالی که منبع ادعا می‌کند یکی نیستند |
| غیرکاتالوگ | پیشوند بازیابی/آزمایش `RECOVERY-CLONE-`، `STAGING-PILOT-` |

تضاد با داده قبلی سامانه:

- اگر `product_code` موجود باشد و `sku` منبع همان باشد → به‌روزرسانی هویت طبق منبع Website (idempotent)
- اگر همان `product_code` با نام یا دسته کاملاً متفاوت بیاید و اپراتور تأیید نکرده باشد → `rejected_ambiguous`، بازنویسی خاموش ممنوع

هیچ‌کدام از ردها با ساخت کد یا برند جبرانی درست نمی‌شوند.

## ۱۰) اعتبارسنجی و جلوگیری از تکرار

قبل از نوشتن در جداول هویت:

1. `sku` پس از trim غیرخالی است و طول از حد ستون بیشتر نیست.
2. `sku` در فایل ورودی به یک مجموعه فیلد هویت پایدار نگاشت می‌شود؛ در صورت تضاد داخل فایل، هیچ نسخه‌ای وارد نمی‌شود تا رفع شود.
3. یکتایی مقصد: `products.product_code` یکتا.
4. کلید نوشتن محصول فقط `product_code` است (همان `sku`).
5. کلید نوشتن برند در محدوده: `(group, category, website_brand_id)` و در نبود آن `(group, category, display_name)` فقط اگر `website_brand_id` موجود نباشد — مورد دوم مبهم گزارش می‌شود و ترجیح با رد است.
6. کلید نوشتن تگ: `(product_code, brand_id)`.
7. تکرار اجرای Import روی داده یکسان ردیف تکراری نمی‌سازد؛ همان کلیدها به‌روز یا بدون تغییر می‌مانند.
8. Import جداول `price_observations`، `final_daily_prices` و `publications` را پر نمی‌کند.

Idempotency:

```text
تکرار Import(منبع با checksum یکسان)
  → محصولات و تگ‌های موجود حفظ می‌شوند
  → شمارش created = 0 (یا فقط موارد جدید واقعی منبع)
  → updated فقط اگر فیلد هویت منبع تغییر کرده باشد
```

کلید عملیات Import در Audit: checksum فایل + نسخه قرارداد + زمان اجرا.

## ۱۱) گزارش نتیجه Import

هر اجرا یک گزارش اجباری دارد. بدون گزارش، اجرا کامل محسوب نمی‌شود.

حداقل فیلدها:

| بخش | محتوا |
| --- | --- |
| منبع | نام فایل/API، checksum، زمان دریافت، نسخه قرارداد |
| شمارش ورودی | تعداد ردیف خوانده‌شده |
| محصولات | created / updated / unchanged / rejected |
| برندها | created / updated / unchanged / rejected |
| تگ‌ها | created / updated / unchanged / rejected |
| بدون برند | تعداد محصول پذیرفته‌شده بدون تگ |
| رد ناقص | فهرست `sku` یا شماره ردیف + علت |
| رد تکراری | `sku`های تکراری داخل فایل و تضاد فیلدها |
| رد مبهم | گروه نامشخص، برند هم‌نام، تضاد با رکورد موجود |
| رد شده غیرکاتالوگ | پیشوند آزمایش/بازیابی |
| نمونه پذیرفته | چند `sku` → `product_code` عیناً برابر |
| هشدار | تگ ردشده روی محصول پذیرفته؛ دسته بدون برند |

گزارش باید برای انسان خوانا باشد و برای Audit قابل ذخیره. محصول ردشده وارد جدول `products` نمی‌شود.

## ۱۲) تکرارپذیری

Import باید بارها با همان خروجی Website قابل اجرا باشد.

- Upsert بر کلیدهای بخش ۱۰
- حذف فیزیکی کالا به‌خاطر نبودن در فایل جدید پیش‌فرض خاموش است (حذف فقط با سیاست جدا و تأیید انسان)
- کالای غایب در منبع جدید می‌تواند در گزارش «در منبع نبود» بیاید ولی غیرفعال‌سازی خودکار ندارد مگر تأیید شود
- ترتیب ردیف فایل روی هویت اثر ندارد

---

## ۱۳) ممنوعیت ساخت از متن قیمت

Import کاتالوگ فقط از خروجی رسمی Website تغذیه می‌شود.

ممنوع:

- ساخت محصول از متن تلگرام، سایت رقیب، PDF یا ورود دستی قیمت
- ساخت برند از نام کارخانه داخل آگهی
- تکمیل `sku` خالی از روی کاتالوگ Excel محلی
- ورود ردیف `catalog.xlsx` به‌عنوان هویت، حتی اگر نامش شبیه Website باشد

تطبیق بعدی قیمت به کاتالوگ واردشده تکیه می‌کند؛ اگر کالا در کاتالوگ نباشد مشاهده `unmatched` می‌ماند، کالای جدید ساخته نمی‌شود.

---

## دامنه خارج از این قرارداد

این سند مشخص نمی‌کند و در این مرحله اجرا نمی‌کند:

- Migration و ایجاد جداول
- اجرای Seed
- نگاشت نهایی شناسه عددی داخلی `brand_id`
- انتقال قیمت `priceToman` / تاریخچه قیمت Website
- پایلوت محدود به میلگرد (می‌تواند فیلتر اجرا باشد، نه استثنای هویت)

پس از تأیید، پیاده‌سازی Import فقط مطابق همین قواعد مجاز است و باز هم بدون ساخت `product_code` جدید.
